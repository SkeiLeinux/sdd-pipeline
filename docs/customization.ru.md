# Настройка под команду

[English version](customization.md)

Пайплайн рассчитан на то, что его адаптируют, а не используют как есть. Большая часть адаптации - настройки в `sdd.config.json`; остальное - шаблоны и скиллы.

## Настройки

| Ключ | По умолчанию | Что меняет |
|---|---|---|
| `artifact_language` | `en` | язык текста, который пишут агенты; заголовки, ключи, статусы и названия полей остаются английскими для скрипта |
| `feature_id_pattern` | `^[A-Z][A-Z0-9]*-[0-9]+$` | ID задач; подстройте под ключи своего трекера |
| `scope` | `{"in": "in", "out": "out"}` | метки колонки Scope, например `{"in": "ours", "out": "external"}` |
| `requirement_types` | `FR`, `NFR`, `BR`, `IR` | допустимые типы требований |
| `ui_domain_prefix` | `ui-` | домены с этим префиксом обязаны иметь таблицу "Screen fields" |
| `unit_types` | восемь типов | типы единиц спецификаций в порядке нумерации; каждому нужен шаблон |
| `api_unit_type`, `data_model_unit_type` | `api-method`, `data-model` | к каким типам применяются правила API и модели данных |
| `contract_kinds`, `contract_modes` | `api, message, file, other`; `new, change, reuse, external` | допустимые значения в контрактах |
| `api_response_required_keys` | `[]` | ключи, которые обязан содержать каждый пример ответа API, - ваша обертка ответа, например `["data", "error"]` |
| `data_model` | `Name, Type, Comment, Constraint`, логические типы | колонки и типы таблиц модели данных |
| `style.forbidden_chars`, `style.forbidden_words` | пусто | стиль команды, сообщается предупреждениями |

Пример строгого стиля:

```json
"style": {
  "forbidden_chars": {"—": "use '-'", "«": "use straight quotes", "»": "use straight quotes"},
  "forbidden_words": {"customer": "say 'user'"}
}
```

## Артефакты на другом языке

Задайте `artifact_language` (например `ru`). Агенты будут писать требования, вопросы, карточки и спецификации на этом языке. На английском остаются: заголовки из шаблонов, ключи шапок, значения статусов, названия полей вроде `- Status:`, заголовки таблиц, ID. Именно это делает проверку независимой от языка. Если нужны локализованные шаблоны - переведите текст и подсказки в `templates/`, но держите заголовки `## ` в согласии с тем, что ожидают скиллы и скрипт, или меняйте и их.

## Новый тип единицы спецификации

1. Добавьте тип в `unit_types` (позиция задает порядок нумерации).
2. Создайте `templates/spec/<тип>.md`. Его заголовки `## ` станут обязательными разделами каждой единицы этого типа.
3. Добавьте правило нарезки в `.agents/skills/sdd-plan/SKILL.md` и, если у типа есть особые правила, в `sdd-spec` и `sdd-review`.
4. Запустите `python tools/sync_agents.py`.

## Правила команды для API и данных

- Стандартная обертка ответа: перечислите ее ключи верхнего уровня в `api_response_required_keys`, опишите ее в шаблоне `api-method` и в правилах `sdd-spec`.
- Версионирование, именование, реестры кодов ошибок: опишите на своей странице в `docs/` и добавьте ее в список "Read" скиллов `sdd-spec` и `sdd-review`.
- Типы данных: подстройте `data_model.types` под свои логические типы и подсказку шаблона.

## Согласование и роли

Пайплайн предполагает только одно: "approved" значит "ответственные люди согласились". Типичная схема: спецификации идут на ревью как pull request; апрувы от разработчиков компонента, потребителей его интерфейсов и QA; владелец ставит `approved` после слияния. Запишите свою матрицу согласования в `docs/pipeline.md` своей копии.

## Описание существующей системы

Для задач, меняющих существующую систему, `sdd-impact` нужно что-то читать: код или описание текущего состояния. Хорошая практика - папка `system/` с карточкой на каждый компонент (назначение, интерфейсы, данные, конфигурация), которая обновляется после внедрения каждой задачи. Тогда спецификации следующей задачи пишутся как изменение описанной системы, а не восстанавливаются по коду.

## Продолжение после спецификаций

Пайплайн намеренно останавливается на согласованных спецификациях. Естественные расширения - каждое как скилл с шаблоном:

- задачи по единицам спецификаций (одна задача - один merge request в один репозиторий);
- тест-кейсы по единицам спецификаций со ссылками на требования;
- план внедрения задачи;
- обновление описания системы после внедрения.

Новые типы ID и проверки добавляйте в `tools/check.py` с тестами, новые ворота - там, где они помогают.
