# Пайплайн: этапы, ворота, изменения

[English version](pipeline.md)

**Задача (feature)** - вся работа по одному входному документу, папка `features/<ID>-<slug>/`. Ее статус - поле `status` в паспорте (`README.md`): `intake -> analysis -> contracts -> plan -> spec -> ready`, а также `hold` и `cancelled`. С продвижением статуса проверка становится строже: правило более позднего этапа до него - предупреждение, после - ошибка.

## Этапы

| Этап | Скилл | Результат | Ворота |
|---|---|---|---|
| 0. Прием | `sdd-intake` | снимок `source/`, паспорт | человек сверил нумерацию с оригиналом |
| 1. Карта доменов | `sdd-map` | `analysis.md`, срезы | владелец утвердил карту (`M-NNN`) |
| 2. Требования | `sdd-domain`, запуск на домен | `requirements/<домен>.md`, вопросы | разобран каждый домен, каждый раздел отнесен к доменам |
| 3. Влияние (по необходимости) | `sdd-impact` | раздел "Impact" в `analysis.md` | прочитал лид |
| 4. Контракты | `sdd-contracts` | `contracts/README.md`, `CON-NNN` | `check.py --gate contracts` |
| 5. План | `sdd-plan` | "Spec plan" в паспорте | покрыты все требования зоны и новые контракты |
| 6. Спецификации | `sdd-spec`, запуск на единицу | `specs/SPEC-NN-*.md` | `check.py` без ошибок |
| 7. Ревью и согласование | `sdd-review`, затем люди | спецификации `approved` | `check.py --gate ready` |

### 0. Прием

Конвертируйте документ в Markdown любым инструментом (для Word: `pandoc input.docx -t gfm --extract-media=. -o input.md`), затем запустите `sdd-intake`. Он создает папку задачи скриптом `tools/new_feature.py` и делает снимок; без агента:

```bash
python tools/new_feature.py PAY-42 refunds --title "Refunds" --owner "Analyst" --source "BRD v3" --input brd.md
```

```bash
python tools/snapshot.py features/PAY-42-refunds/source/import/brd.md features/PAY-42-refunds/source
```

Несколько документов на одну задачу (требования плюс дополнение) - объедините в один Markdown, каждый под своим заголовком верхнего уровня: одна задача - один нумерованный источник. Картинки и относительные ссылки продолжают работать: снимок и срезы переписывают их пути. Скрипт сохраняет текст и приводит заголовки к нумерованным разделам (`--number` пронумерует их, если в документе нумерации нет). Человек проверяет, что нумерация совпадает с оригиналом, а таблицы и картинки пережили конвертацию.

### 1. Карта доменов

`sdd-map` один раз читает снимок целиком и предлагает вершины, ребра, сценарии, сквозные правила, список "Read" для каждого домена и указатель, относящий каждый раздел к доменам. Скрипт собирает срезы по спискам "Read". Владелец утверждает или правит карту; агент записывает это как `M-NNN`.

Хорошая карта: каждый домен помещается в один запуск агента; внешние системы появляются только на концах ребер; ни один раздел не остался без отнесения.

### 2. Требования по доменам

`sdd-domain` берет один домен за запуск и читает только его срез. Каждое проверяемое утверждение становится требованием с разделом источника, типом и зоной (`in` - пишем на него спецификации; `out` - это работа другой системы). Пробелы становятся вопросами. Требование для другого домена попадает в "Findings for domains" и подбирается при разборе того домена. У UI-доменов есть еще таблица "Screen fields": каждое поле и действие, правило за ним и операция, которая его наполняет.

Порядок: сначала вершины бэкенда и ребра, UI-домены последними.

### 3. Влияние

Если задача меняет существующую систему, `sdd-impact` фиксирует, какие компоненты меняются, где в коде или документации, что переиспользуется и что рискованно. Для новой разработки - "Not applicable".

### 4. Контракты

`sdd-contracts` перечисляет каждый интерфейс по ребрам: новые и изменяемые, которыми владеем мы, и существующие или внешние, которыми только пользуемся. Каждое требование зоны связано с контрактом или объяснено, почему контракт не нужен. Реестр переходит в `review`, и до планирования должны пройти ворота `--gate contracts`. Владельцы обеих сторон каждого интерфейса читают карточки.

### 5. План

`sdd-plan` распределяет требования и контракты по единицам спецификаций по правилам нарезки (один метод - одна единица, одна модель данных на компонент и так далее) и заполняет таблицу плана в паспорте, сгруппированную по доменам.

### 6. Спецификации

`sdd-spec` пишет одну единицу за запуск в рекомендуемом порядке: компонент и модель данных -> интеграции и фоновые задачи -> методы API -> сценарии и экраны -> конфигурация. Полный контракт интерфейса проектируется здесь, с источником для каждого значения. Единицы можно отдавать на ревью по одной, ждать весь комплект не нужно.

### 7. Ревью и согласование

`sdd-review` в новой сессии выдает замечания и вердикт. Само согласование - за людьми: обычно это апрувы pull request от разработчиков компонента, потребителей его интерфейсов и QA. После слияния владелец ставит `approved`. `--gate ready` проверяет, что все запланированные спецификации и используемые контракты согласованы, нет открытых блокирующих вопросов и не осталось маркеров.

## Изменения по ходу работы

### Пришли ответы

`sdd-decide` применяет их: решение переносится в `decisions/decisions.md` под тем же ID, маркеры убираются, требования, карточки и спецификации обновляются. Согласованный артефакт не правится - о новой версии решает его владелец.

### Новая версия входного документа

Положите ее в `source/import/` и запустите `sdd-update`. Снимок заменяется, `source/changes.md` перечисляет измененные, добавленные, удаленные, переименованные и перенесенные разделы, срезы пересобираются. Скилл прослеживает изменения до доменов, требований, контрактов и спецификаций и обновляет черновики. Требования никогда не удаляются: их исключают или заменяют в `requirements/dispositions.md` с причиной.

### Кто-то нашел проблему в спецификации

Остановить затронутую работу - никаких "сделаю как правильно". Завести вопрос, сначала поправить контракт, если меняется интерфейс, затем спецификацию: `version + 1`, статус `review`, строка в "History", повторное согласование.

## Публикация спецификаций для читателей вне git

Согласование часто идет там, где бизнес читает документы. Спецификации - обычный Markdown, подойдет любой конвертер, например:

```bash
pandoc features/PAY-42-refunds/specs/SPEC-06-api-create-refund.md -o SPEC-06.docx
```

Источником правды остается Markdown в git: замечания из вики или Word возвращаются правками спецификации, а не наоборот.

## После спецификаций

Пайплайн заканчивается согласованными спецификациями. Задачи, код, тесты и внедрение - по вашему процессу. Полезная договоренность: указывать `<ID задачи>/SPEC-NN` и `REQ-NNN` в названиях задач, merge request и тестов, чтобы цепочка к источнику не рвалась. Пайплайн можно дополнить своими этапами - см. [customization.ru.md](customization.ru.md).

## Сводка ворот

| Ворота | Когда | Как |
|---|---|---|
| Вход принят | конец этапа 0 | человек проверил снимок |
| Карта утверждена | конец этапа 1 | владелец, `M-NNN` в `decisions/manual.md` |
| Разбор завершен | до контрактов | `check.py` при статусе `contracts`: у каждого домена есть требования, каждый раздел отнесен, находки учтены |
| Контракты описаны | до плана | `check.py --gate contracts` |
| План составлен | до спецификаций | `check.py` при статусе `spec`: покрытие требований и контрактов |
| Готово | после согласования | `check.py --gate ready` |
