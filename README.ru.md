# SDD-пайплайн: от требований к спецификациям с ИИ-агентами

[English version](README.md)

Пайплайн spec-driven development (SDD). На вход - структурированный документ требований (бизнес-требования, функциональное задание, PRD), на выходе - набор небольших прослеживаемых спецификаций, удобных для ревью: один метод API, одна модель данных, один экран, одна интеграция - один файл.

Черновики пишут ИИ-агенты. Решают и согласуют люди. Детерминированный скрипт следит за формой и трассировкой.

```mermaid
flowchart LR
  A[Документ требований] --> B[Снимок<br/>неизменяемый, с нумерацией]
  B --> C[Карта доменов<br/>компоненты и обмены]
  C --> D[Требования<br/>по доменам + вопросы]
  D --> E[Контракты<br/>сначала интерфейсы]
  E --> F[План спецификаций]
  F --> G[Единицы спецификаций<br/>по одной на файл]
  G --> H{Ревью и согласование}
  H -->|замечания| G
  H --> I[Готово к разработке]
```

## Что это

- **Метод.** Десять принципов с обоснованием: почему входной документ не правится, почему требования режутся по компонентам, а не по разделам документа, почему интерфейсы перечисляются до планирования, почему "не знаю" должно быть учтенным вопросом. См. [docs/concepts.ru.md](docs/concepts.ru.md).
- **Набор для агента.** `AGENTS.md`, десять скиллов (по одному на шаг), два субагента, шаблоны и полный пример. Работает с Claude Code, Codex, Kilo Code, OpenCode и с любым агентом, который читает `AGENTS.md`.
- **Инструменты.** Три скрипта на Python только со стандартной библиотекой: `snapshot.py` (нумерованный снимок входа), `slices.py` (срезы снимка по доменам), `check.py` (форма, ссылки, покрытие, ворота, трассировка). Покрыты регрессионными тестами.

Чем это не является: конвертером из Word или вики (приносите Markdown, сделанный любым инструментом), системой управления проектами или генератором кода. Пайплайн заканчивается согласованными спецификациями; задачи, код и тесты строятся по ним вашим процессом.

## Быстрый старт

1. Скопируйте репозиторий (или используйте как шаблон) и откройте его в своем агенте.
2. Конвертируйте документ требований в Markdown и положите в `features/<ID>-<slug>/source/import/`.
3. Запускайте скиллы по порядку, каждый в новой сессии агента:

| Шаг | Скилл | Результат |
|---|---|---|
| 1 | `sdd-intake` | снимок `source/source.md`, паспорт `README.md` |
| 2 | `sdd-map` | карта доменов `analysis.md`, срезы `source/domains/` |
| 3 | `sdd-domain` (на каждый домен) | `requirements/<домен>.md`, вопросы |
| 4 | `sdd-impact` (по необходимости) | влияние на существующую систему |
| 5 | `sdd-contracts` | `contracts/README.md`, карточки `CON-NNN` |
| 6 | `sdd-plan` | план спецификаций в паспорте |
| 7 | `sdd-spec` (на каждую единицу) | `specs/SPEC-NN-*.md` |
| 8 | `sdd-review` (на каждую единицу) | замечания и вердикт |
| в любой момент | `sdd-decide`, `sdd-update` | применены ответы, учтена новая версия входа |

4. Проверка в любой момент:

```bash
python tools/check.py features/<ID>-<slug>
```

Начните с [examples/LIB-1-book-reservations](examples/LIB-1-book-reservations/README.md): вымышленная задача библиотеки, проведенная через все шаги; часть вопросов и спецификаций намеренно оставлены открытыми.

## Структура репозитория

| Путь | Что там |
|---|---|
| `AGENTS.md` | правила, которые агент читает всегда |
| `.agents/skills/` | скиллы пайплайна `sdd-*` (источник правды) |
| `.agents/subagents/` | инструкции `sdd-check` и `sdd-source` |
| `.claude/`, `.kilo/`, `.opencode/` | адаптеры под конкретные инструменты |
| `templates/` | шаблоны всех артефактов |
| `examples/` | полный пример задачи |
| `features/` | ваши задачи |
| `tools/` | скрипты и их тесты |
| `sdd.config.json` | настройки проекта: язык, метки зоны, типы единиц, правила команды |
| `docs/` | документация |

Скиллы, шаблоны и правила агента написаны на английском: их читает модель. Документация для людей есть на обоих языках. Язык, на котором агент пишет сами артефакты, задается в `sdd.config.json` (`artifact_language`).
